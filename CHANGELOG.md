### Install from the GitHub Release
- The npm name `openband` belongs to someone else (a reserved 0.0.0 package), so `npx openband` would run code that is not OpenBand's. OpenBand now installs from its GitHub Releases: each release carries the built package (`openband.tgz`, also as `openband-X.Y.Z.tgz`) next to the Claude Desktop extension (`openband.mcpb`). The app, the CLI, `setup`, `doctor`, update notices and bug reports all show the same command (`server/package.mjs`, `src/install.ts`, a test keeps them equal). `--allow-remote=all` is needed by npm 12 (Node 26), which refuses tarball URLs by default; npm 10 and 11 ignore it.
- `setup` writes the version-pinned release URL into MCP client configs; `doctor` flags entries that run the npm package `openband` and tells you to rerun setup. Update notices read the latest GitHub Release.
- The release workflow attaches the package and the extension; publishing to npm and pushing the Docker image to GHCR are opt-in (repository variables `NPM_PUBLISH`, `PUBLISH_DOCKER`).
- A new demo GIF (`scripts/record-demo.mjs` records it: the studio driven over MCP, from the welcome screen to a song built from one request and playing with the mixer) and fresh mixer and piano roll screenshots (`--shots`).
- Fixed: a key written in words (`"D minor"`, `"Bb major"`, `"A# min"`) given to `new_project` or `set_key` was stored as is and showed as C; keys are now normalized to the studio's spelling (`Dm`, `Bb`, `Bbm`), and anything that is not a key is refused with an example.
- README rewritten: three ways in (demo, Claude Desktop, one command), your first song in four steps; the full feature list, the MCP tool reference and the development guide moved to [docs/FEATURES.md](docs/FEATURES.md), [docs/MCP-TOOLS.md](docs/MCP-TOOLS.md) and [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

### F16 delta · Versions and comment threads shared in rooms
- Versions in the room: every peer's saved versions (metadata and the gzipped snapshot) and branch heads live in the Y.Doc (`src/collab/shared.ts`: `versions` and `branches` maps). On joining, your versions of the song go into the room and the room's are stored in your browser; from then on every version saved and every branch moved by anyone reaches everyone. Versions never change once saved, so concurrent saves simply all appear; when two people move the same branch head at once, the newest move wins everywhere (`BranchRef.at`; each peer writes its own entry and readers take the newest — Yjs alone settles concurrent writes of one key by client id, which a first version relied on and the test caught). The Versions panel, `list_versions`, checkout and merge work on the shared history.
- Comments as multi-person threads: `Annotation.author` is now `{kind: 'user' | 'ai', name}` — in a room your name, and the AI acting through your browser is *AI · <your name>* — and `replyTo` links an answer to the comment it answers. `annotate` takes `reply_to` (the target is then taken from it); `list_annotations` returns author and `reply_to`; the Comments panel shows names and nests replies. Older songs are migrated (`'ai'` → *AI*, `'user'` → *You*).
- Tests: convergence with two Y.Docs working offline and then exchanging updates — versions saved concurrently by two people both kept with identical snapshots, concurrent branch moves resolved to the newest everywhere, comments from two people and an AI (a reply arriving while the question is resolved) identical on both sides with authors and links; the author migration. In two Chrome tabs in a LAN room: a version saved before the room reached the joiner, versions saved by each reached the other, and an AI comment with a reply from the other person showed both names.

### F25 · Multi-input recording, punch-in and pre-roll
- Input device selection (`enumerateDevices`) in the microphone menu; the recording worklet now forwards every channel of the device (`getUserMedia({channelCount})`, discrete channels), and each armed track takes its own: e.g. input 1 → Vocal, input 2 → Guitar.
- **Arm** per audio track (the **R** button in the track header): several armed tracks record together in one pass, each into its own clip.
- **Punch in/out** on a bar range with a **pre-roll** of N bars (the song plays, the recording starts at the punch-in and stops at the punch-out; the song's loop is suspended meanwhile). Over an existing clip the result is a new take of that clip — the old audio with only the punched range replaced, joined by 5 ms equal-power crossfades (`src/punch.ts`, pure) — else a new clip. A red band shows the range on the ruler.
- **Loop recording**: with the cycle on (and no punch), every pass becomes a take of one clip over the cycle, the last one active (F12).
- Optional **input monitoring**, with a warning when the device's latency is noticeable (over 12 ms).
- Arming, punch and device are session settings (not undo steps, like in other DAWs).
- Tools: `arm_track({track_id, input_channel, armed?})`, `set_punch({in_bar, out_bar, pre_roll_bars, enabled?})`, `record_audio` uses them (`use_setup`, default true) and lists every recorded clip. 129 tools.
- Tests: a 2-bar punch replaces only that range (outside the crossfades the original is bit-identical, inside only the new audio), crossfades of exactly 5 ms without a jump, pre-roll plans (also at the song start), loop passes, monitor latency. In Chrome with a fake 2-channel interface (220 Hz on input 1, 440 Hz on input 2): two armed tracks recorded together got 220 and 440 Hz; a punch on bars 2–3 with a 1-bar pre-roll (input 1 now at 660 Hz) produced Take 2 with 220 / 660 / 220 Hz in bars 1 / 2–3 / 4 and no larger sample step at the seams than inside; a 3-pass cycle recording produced 3 takes.

### F24 · Drummer and CC0 loop library
- Drummer (`src/generate/drummer.ts`, pure and deterministic — no LLM): 10 styles (rock, pop, funk, boom-bap, trap, lo-fi, house, bossa, ballad, shuffle), each a grammar of 16-step lines with probabilities, extra lines that complexity unlocks, ghost notes, accents, humanized velocity and timing, swing (16ths, or 8ths for shuffle), fills at the end of sections or every 4 bars (toms, snare or hat rolls per style) and a crash after them. The section's energy (F8) scales complexity and loudness: simpler in verses, fuller in choruses. Hits of the same drum are never closer than a 32nd (a monophonic drum voice can't play them — found when the loop builder crashed on one).
- Tools: `add_drummer({track_id?, section_id? | from_bar…to_bar, style, complexity, loudness, swing, fills, seed?})` — for a section, a range or the whole song, on the drum track or a new one with the kit for the style; the region remembers how it was made. `regenerate_drummer({region_id, seed?, as_take?, …})` — the next seed by default, optionally another style; as a take for a blind test (F12).
- Loop library: 16 loops (8 drum grooves, 3 bass lines, 3 keys, a pad, a chiptune arpeggio; 72–140 BPM, 2 bars each, 3.2 MB) in `public/loops/` with `index.json` (`{id, name, bpm, key?, bars, tags, license: 'CC0', author, url, source}`) and `LICENSE.txt`. They are **made with OpenBand's own instruments** by `scripts/build-loops.mjs` (recipes in the script: the drummer, note lines, chord progressions; rendered in headless Chrome, the tail folded back so they repeat seamlessly, 22.05 kHz mono WAV) and dedicated to the public domain by the OpenBand contributors — no third-party audio, so their CC0 status is certain. The manifest also takes https URLs of other CC0 sources. Loop audio is cached on first use, not precached by the service worker.
- *Loops* tab in the library: search (also Italian words), *Near <tempo>*, *In <key>*, tags, preview at the song's tempo and key (on the next bar when the song plays), *Add* at the playhead. Added loops follow the song tempo (F23) and are transposed to the song key when they have one (same mode only); the new track is named after the loop.
- Tools: `search_loops({query, bpm?, key?})`, `add_loop({loop_id, track_id?, start_bar, repeat?, follow_tempo?, match_key?})`. 127 tools.
- **Fix (D10):** a page served on localhost that switched to *Claude (remote)* could open a second remote connection from its normal bridge's pending reconnect, which got a new code while the first one was paired (the tab then showed a code although paired; an intermittent e2e failure). Switching cancels the pending reconnect and only one remote connection is ever open.
- Tests: same seed → same part (inline snapshot), every style plays a groove inside its bars with no doubled hits, verse < chorus, loudness and complexity, fills and crash placement, swing, spans from sections; the commands (whole song, one section, regenerate as take, errors); the manifest (every loop CC0 with author and source, files present, exactly `bars` long, total ≤ 5 MB, invalid entries refused), search and key matching. In Chrome: a funk drummer over verse and chorus, an Em bass loop added into a Dm song at 96 BPM (transposed −2, following the tempo), a pad, playback, export and a preview from the Loops tab, with no errors.

### F23 · Time-stretch and pitch-shift of audio clips
- `src/audio/stretch.ts` (pure, no dependency, no GPL code — Rubber Band is not used): **WSOLA** for stretching (≈23 ms frames, waveform-similarity search; frames containing an attack are placed so that the attack lands exactly on its stretched time) and a **phase vocoder with identity phase locking** plus cubic resampling for pitch. Runs in a worker (`workers/stretch.worker.ts`) with a cache of processed buffers by (sample, factor, semitones) (`audio/processed.ts`), used by the live engine and the offline render alike; 3 ms fades at both ends.
- Model: `AudioClip.stretch?: {mode: off | follow_tempo | fixed, ratio?, originalBpm?}` and `pitch?` (semitones, decimals = cents). follow_tempo: the clip plays at the song tempo from its original BPM, keeping its length in beats when the tempo changes; fixed: played length / original length.
- Tempo of a loop, estimated at import (kept on the clip, stretch off): from the file name (`loop_92bpm.wav`, `Funk 120 BPM.wav`) or from an onset envelope's autocorrelation, snapped to a whole number of bars when close. `detect_tempo({sample_id | region_id, apply?})`.
- Clip editor: *Stretch* (Off / Follow tempo (92 BPM) / Fixed ratio), *Detect BPM*, *Pitch*; waveforms show the stretched clip. Changing the key in the display offers *Transpose N audio clips ±k* (one undo step); `set_key({key, transpose_audio})` does it for the AI (the short way, up to a tritone).
- DAWproject: a warp map now becomes a fixed stretch (several markers are simplified to one ratio and reported); stretched clips export with the matching warp; pitch shifts are listed as not exportable.
- Tools: `update_region` takes `stretch_mode`, `ratio`, `original_bpm`, `pitch`; new `detect_tempo`; `set_key` takes `transpose_audio`. 123 tools.
- Decision record and comparison on three materials (voice-like vowel, drums, pad; transients kept, pitch error, edge jumps, speed): [docs/adr/0002-time-stretch.md](docs/adr/0002-time-stretch.md); `scripts/stretch-compare.mjs` regenerates it and writes WAVs for a listening test, which has **not** been done by people yet.
- Tests: 0.8× / 1.25× with the right length and no clicks at the edges or inside; a 100 BPM loop at 120 BPM with every onset within 5 ms of the grid (the spec asks ±10 ms); ±3/−5 semitones within 1% of the target pitch with the length kept; stretch and pitch together; tempo from audio (92, 128, 75 BPM within 1) and from names; the commands (follow_tempo keeps 2 bars at any tempo, fixed ratio, pitch, errors, key transposition). In Chrome: a 92 BPM loop imported into a 120 BPM song, detect_tempo + follow_tempo → exactly 2 bars, exported onsets 1–4 ms from the grid, playback through the worker without errors.

### F22 · Automation of effect and plugin parameters
- Schema v3: `Track.automation` is a list of lanes `{target, points}` with open targets — `{kind:'mix', param}` (volume, pan, tone, reverb, echo), `{kind:'fx', unit:'amp'|'eq'|'comp', param}` (drive, tone, level · low, mid, high, midFreq · threshold, ratio, attack, release, makeup) and `{kind:'plugin', slotId (null = the plugin instrument), paramId}`. Values in the parameter's own range (plugins: from `getParameterInfo`). Migration v2 → v3 converts the old `{volume: […], …}` records (tested); every module that read them (engine, render, structure edits, canonical form, DAWproject, the lane UI) goes through `src/automation.ts`.
- Live and offline: mix lanes as before; effect lanes on the built-in units at audio time (`FxChain.setParam`); plugin lanes as `wam-automation` events (`setParameterValues` where a plugin takes no events). Offline, plugin automation is sent during the render at each 20 ms step (with a little main-thread time per step) and automated plugins get a 0.5 s lead-in that is trimmed: posting every event before the render — what the transport does — made plugins apply them late, and a plugin starts from its saved state and glides from there. Without these the export was up to 4 dB off live in the first second; with them, the end-to-end check below passes.
- Recording automation: each lane has Read / Touch / Latch. While the song plays, moving any fader or knob of the mix or of the built-in effects writes its lane at the playhead (one undo step per gesture); Touch returns to the previous curve when you let go, Latch holds the last value until playback stops. AI commands never write. (Moves made inside a plugin's own window are not recorded.)
- UI: the lane selector lists Mix / Amp / EQ / Compressor and every loaded plugin's parameters, with a dot on those that have a curve; values shown in dB, Hz, ms, ratio or L/R. A lane key that is unknown or stale falls back to the volume lane instead of breaking the arrangement (a crash found while testing).
- Tools: `set_automation` takes a `target` (the `param` signature still works), `clear_automation` too; new `list_automatable({track_id})` with every target, its range and whether it has a curve; `get_project` lists curves by key (`volume`, `fx:eq.midFreq`, `plugin:<slot>:<param>`). 121 tools.
- `?debug` puts the engine and the store on `window.openband` (diagnostics and end-to-end tests); `engine.captureMaster(seconds)` records what the master plays.
- Tests: migration, target keys, `set_automation` with targets and clamping, touch and latch through the real store, plugin lanes as scheduled events (and the fallback). E2E `automation` (also in CI): a GraphicEqualizer high-pass swept 40 Hz → 3 kHz on a square wave, captured live and rendered: every 100 ms window within 1 dB (0.64–0.77 dB worst, 0.12 dB mean), while the export without the sweep is 5 dB off — so the check is sensitive. A detuned synth differs by ~1.2 dB between live and export even with nothing automated (random oscillator phase), which is why the test uses a square wave.

### F17 · DAWproject import and export
- `src/interop/dawproject/` (pure): `xml.ts` (DOMParser in the browser, `@xmldom/xmldom` in the Node tests — devDependency only; a small escaping writer), `import.ts`, `export.ts`, `report.ts`. Written from the public schema of `bitwig/dawproject` (MIT; `Project.xsd` and `MetaData.xsd` are vendored in `schema/` with their license, for the tests).
- Import: tempo (tempo changes → report), time signature (≠ 4/4 → report), tracks with their channels (volume linear / dB / normalized → fader, pan, mute, solo, colour), folder tracks flattened (report), master volume; note clips (beats or seconds, `playStart`, loops unrolled, nested clips) and audio clips (through `Warps` or `Audio`, offset from the warp map; stretched audio is imported at its original speed and reported until F23); markers → sections (an "End" marker closes a section); volume/pan `Points` → automation, other targets → report; built-in `Equalizer` (shelves and bell) and `Compressor` → OpenBand's EQ and compressor; instrument plugins → the closest preset by name (piano, rhodes, bass, pad, strings, drums… — e.g. *Surge XT* on a track called Bass → Sub Bass), other plugins → report with name and format; sends: the largest to reverb, the next to echo (report); scenes / clip slots, video, clip fades, missing audio → report.
- Export: `project.xml` (validated against the official XSD with `xmllint` in the tests), `metadata.xml`, the audio files, and `openband.json` with what DAWproject can't hold (lyrics, takes, comments, flubs, WAM plugins, the amp sim, tone/reverb/echo automation — listed in the export result). Re-importing an unchanged OpenBand export restores it exactly (hash of project.xml); one changed by another DAW is converted, then gets its lyrics, key and instrument choices back by track name.
- UI: *⋯ → Import DAWproject… / Export DAWproject*, drag & drop, and *Open with* for the installed app (D5); after an import the *What wasn't imported* dialog lists the report. Replacing the song saves a "Before: import DAWproject" version first (F21); exports never overwrite (`song v2.dawproject`).
- Tools: `import_dawproject` (file path or URL; `replace` default true, false adds the tracks; returns tracks, regions, sections, source application and the report), `export_dawproject` (`save_to`). 120 tools.
- Fixtures: two `.dawproject` files in `src/__fixtures__/dawproject/`, **written by hand** following the schema — one in the shape of a Bitwig Studio 5 export (from the format's README example: Surge XT, a time-stretched drum loop in nested clips, EQ+ automation, a scene), one in the shape of a Studio One 6.5 export (a folder track, FX channels with dB sends, built-in EQ and compressor, tempo changes, a looped clip, a timeline in seconds, a missing audio file). Both validate against the XSD; they are not files exported by those applications (no Bitwig or Studio One here), so files from the real programs may still surprise the importer. `scripts/build-dawproject-fixtures.mjs` rebuilds them.
- Tests: both fixtures imported with the expected tracks, notes, conversions and report; OpenBand → DAWproject → OpenBand equal on `canonical.ts`; the same file read without `openband.json` keeps every portable part (tracks, mixer, EQ/compressor, notes, sections, automation, audio offsets); the exported XML valid against the XSD (structural check where `xmllint` is missing). In Chrome: MCP import of a fixture by path (sample stored), the menu's file picker with the report dialog, and export → re-import identical.

### F21 · Safety net: journal, crash recovery and time machine
- Journal (IndexedDB store `journal`, DB v4, indexed by song): every step that closes — an edit, an AI request, undo, redo, opening a song — appends `{at, label, source, patch}`. The patch is a structural JSON diff (`src/journal/patch.ts`: objects key by key, arrays of objects with ids — tracks, regions, notes, sections — by id, so moving a note stores one small op); a full checkpoint every 50 entries or 10 minutes; everything gzipped. (The F13 diff in `versions/diff.ts` describes changes for people; the journal needs one that can be applied, hence its own.)
- Crash recovery: at start, when the journal holds a later state than the autosave, a banner says "I recovered 14 changes made after the last save" with Restore (one undo step) / Ignore.
- Time machine (Versions panel): a slider over everything journaled; *Preview* opens the song as it was in the compare view (colours, A/B listening against now), *Restore this moment* replaces the song (undoable), *Open as branch* saves it as a version on a new branch and checks it out.
- Automatic versions "Before: …" ahead of destructive operations: `new_project`, `import_project_json`, `checkout`, `merge`, `delete_track` with regions, `restore_at`, and AI requests reaching 21 commands (the state before the request). Nothing is saved for an empty song or one equal to the current version; when the operation replaces the song, the version goes to the song it was taken from. (`import_dawproject` will use it too, with F17.)
- Exports never overwrite: saving `song.openband` again in this browser gives `song v2.openband`, `song v3.openband`…
- Retention: 30 days or 200 MB per song; the state at the new start becomes a checkpoint, so everything after it can still be rebuilt.
- Tools: `get_timeline({from?, to?})`, `preview_at({time})` (a summary like get_project; time as ISO, ms or relative "-20m"), `restore_at({time, as_branch?})` (destructive). 118 tools.
- Tests: patch round-trips; 500 random commands through the real command API (tracks, regions, notes, moves, automation, sections, undo/redo…) with the state rebuilt at every instant equal to the recorded one, also after reloading from storage and after compaction; a simulated crash (journal 14 steps ahead of the autosave) recovered exactly, as one undo step; no banner when the autosave is current; export names. In Chrome with the real IndexedDB: timeline, preview (absolute and relative), restore and its undo, auto versions landing on the right song, and a crash simulated by rolling back the autosave and reloading → banner → Restore gives back exactly the lost state.

### F20 · Monitoring essentials
- Live LUFS meter on the master and on every track: an AudioWorklet (`src/audio/worklets/loudness.worklet.ts`) running the streaming BS.1770 DSP (`loudness-dsp.js`: 100 ms blocks → momentary 400 ms, short-term 3 s, gated integrated since reset, 4× oversampled true peak with hold, reset). The DSP is plain JavaScript loaded as text into the worklet, so no bundler transform can break it there (the first version, a TS class copied with `toString()`, failed in the production build because of class-field helpers — caught in the browser check). Tested against the offline `loudness.ts` on sines, noise, a signal with loud and quiet parts (gating) and a two-tone K-weighting case: integrated and momentary within 0.3 LU, true peak within 0.1–0.15 dB.
- **Fix:** the K-weighting filters (offline and live) are now the standard bilinear-transform design (as libebur128), reproducing the coefficients published in BS.1770 at 48 kHz; before, an RBJ-style derivation read 0.26 dB low (a 0 dBFS 997 Hz sine gave −3.27 instead of −3.01 LUFS). All loudness numbers (analyze_mix, reference matching, the linter) move up by about 0.26 LU.
- Target selector (Streaming −14, Apple −16, Broadcast −23, Club −8, with their true-peak ceilings) and a green / yellow / red light (within 1 LU / 3 LU / beyond or over the ceiling), remembered in the browser. The panel sits next to the master strip.
- **Mono** (L+R summed) and **Dim** (−20 dB) on the monitor stage after the master: what you hear only. Exports render their own graph — checked in Chrome: the exported WAV is byte-identical with Mono and Dim on.
- **Ø** polarity per track (`Track.polarity`, `update_track({polarity})`), in the live chain and in the render (the export changes — checked).
- **A/B level-matched** for the whole FX chain (Effects panel) and for each plugin slot: renders 3 s of the track from the playhead (or its first region) with and without the chain / plugin, compares short-term loudness, says by how much the effect changes the level, lets you hear it bypassed with that gain (both sides equally loud), and *Compensate* writes the difference into the chain's output trim (`TrackFx.trim`, rendered; one undo step). In Chrome an EQ boost read +5.8 dB and, after compensating, +0.02 dB.
- Tools: `get_meters` (read-only), `set_monitoring({mono, dim, target, reset_meters})`, `level_match({track_id, slot_id?, apply?}) → {gain_change_db, …}`, `update_track({polarity})`; instructions tell the AI to level-match before judging an effect. 115 tools.
- The optional "safe solo" is the Dim button (−20 dB instead of silence); dimming the other tracks while soloing was not built.

### F19 · Undo that includes plugin state
- A plugin's whole state (`getState()`: presets, modes, wavetables, anything its GUI changes — not only automatable parameters) is now part of every undo step: it lives in the project (`fx.plugins[].state`, the instrument's `wam.state`), so each history snapshot carries it (`src/pluginHistory.ts`).
- GUI edits: while a plugin window is open its state is polled every 750 ms and hashed (CRC32 of a key-sorted JSON); a change opens an automatic "Edit <plugin>" step, extended while you keep tweaking and closed after 1.5 s of quiet. The first reading after opening is the baseline: opening or closing the window never makes a step.
- Undo, redo, checkout and loading apply the project's state to the live plugins with `setState` when it differs from what they have; meanwhile polling is paused and the studio shows a spinner over everything, so the restore can't be mistaken for an edit or raced by a click. What the plugin reports after `setState` becomes the new baseline (plugins may serialise differently from what they were given).
- `set_plugin_params` (AI) records the resulting state as a normal edit: undoable, grouped with the rest of the AI's request.
- Memory: history keeps at most 50 MB of plugin state, newest first; older steps lose it (`pluginStateDropped`, `plugin_state_dropped` in `get_history`) and undoing to them leaves plugins as they are. States are not compressed in history (the cap bounds the memory instead).
- `get_history` lists `plugins_changed` (plugin names) for every step. No new tools.
- Tests with a fake WAM whose state is not just parameters: GUI edit (several polls) → one step; undo → the exact original state; redo → the edited one; no step from opening/closing the window or from applying a state; `set_plugin_params` undoable; unrelated edits don't touch the plugin; the 50 MB cap (newest kept). Checked in Chrome with a catalog plugin (Simple Delay): opening its window adds no step, `set_plugin_params` 0.3 → 4.5 is undone back to exactly 0.3 and redone.
- The plugin parameter events (`wam-automation`) suggested by the spec are not used: polling covers every plugin, including those that don't send them.

### F18 · Flub markers
- While recording, **F** marks a mistake and **G** a good part (with musical typing open, where F and G play notes: Shift+F / Shift+G); outside a recording F still opens Effects. A MIDI pedal marks mistakes too: CC64 by default, or any controller learned from the *To fix* panel (*Learn*; kept in this browser), only on the way down and only while recording.
- Model: `Project.flubs?: Flub[]` (`{id, beat, trackId, regionId, takeId, kind: flub|good|note, text, createdAt, resolved, author}`), optional, no schema bump. Marks made during a take wait and are stored with the recorded region in the same undo step, bound to it and — in cycle recording — to the take of their pass; a take that records nothing keeps its marks. Marks follow their region when it moves or changes track; deleting the region keeps them unlinked.
- *To fix* panel: the list with bar.beat, track and take, jump (2-bar loop around the mark), *Best take*, *Fixed*, delete. `]` / `[` jump to the next / previous open mistake with that loop. Red, green and grey flags on the ruler, inside the region (for the take that plays) and on the take lanes of the Takes dialog.
- *Best take* (`replace_with_best_take`): among the takes with no mistake within ±1 beat of the mark, the one with the most good marks (then fewer mistakes, then the newest) is comped in over the bars around the mark — the rest stays the active take; audio takes switch as a whole. The mark becomes resolved; one undo step.
- Tools: `add_flub`, `list_flubs`, `resolve_flub`, `delete_flub` (destructive), `replace_with_best_take`; a `flub` studio event for each mark (get_events / wait_for_event), and the server instructions tell the AI to offer fixes. 112 tools.
- Tests: the take-choice algorithm (±1 beat edge, good marks, ties, first take for unlinked marks), the fix window and the 2-bar loop, next/previous with wrap, pedal learn and edge detection, and with the real recorder: a 2-pass cycle recording where a pedal mark and a G mark land on the right takes, follow the region to another bar and track, are fixed with the best take (and come back with undo). Checked in Chrome with real key presses.

### D10 · Remote MCP: OpenBand as a claude.ai connector

### F5 · `analyze_mix`: the AI hears the mix
- Pure DSP in `src/analysis/`: radix-2 FFT with Hann window; ITU-R BS.1770-4 / EBU R128 loudness (K-weighting at any sample rate, gated integrated, short-term max, LRA, 4× true peak, RMS, crest, clipped samples); band energies (sub … air), centroid and 1/3-octave curve; stereo correlation, width (overall and per band), mono loss; masking between stems; key detection (Krumhansl–Schmuckler from MIDI or from an audio chromagram); rules that turn metrics into issues with concrete suggestions.
- Heavy work runs in `src/workers/analysis.worker.ts`; spectrograms are drawn on an OffscreenCanvas (log frequency, perceptual colormap, bar grid, section names).
- MCP tools: `analyze_mix` (range or section, per-track stats, `summary`/`full` with loudness per bar), `render_spectrogram` (returns an MCP image Claude can see), `detect_key`.
- The mix is analysed as the exact sum of its stems (renders are deterministic since F4): the demo is analysed in ~6 s.
- Relative keys (e.g. C / Am) are reported with `same_scale` and not flagged as a mismatch.
- Analysis panel (N) with LUFS/true-peak meters, band bars, per-track loudness, issues and spectrogram; *Analyze* button in the mixer.

### F3 · Studio → AI event channel
- The browser now reports what the user does: live phrases (split after a bar of silence, notes quantized to 1/16 with the raw start kept), selection (throttled to one event per 500 ms), play/stop/loop, finished user edits, recorded regions and questions from the new *Ask the AI* box.
- MCP server: a 500-event ring buffer with the new tools `get_events` (since_id, kinds, limit) and `wait_for_event` (long-poll up to 60 s, `{timeout:true}` otherwise).
- MCP resource `openband://project` (the `get_project` JSON) with subscriptions: subscribers get `notifications/resources/updated` after every change.
- Privacy: *Share my activity with the AI* in the AI panel (on by default on localhost); when off only explicit events (questions, A/B results) are sent.
- Pure modules with tests: `src/phrases.ts` (phrase segmenter) and `server/events.mjs` (event buffer).

### F4 · Reusable renderer
- `renderBuffer(project, options)` renders the song or a range (`fromBeat`/`toBeat`), only some tracks (stems, ignoring mute/solo), with or without the master volume, at any sample rate and with a configurable tail; notes and audio clips already sounding at the start of the range are rendered from the right point.
- `renderStems()` renders tracks one at a time over the same range; `renderProject()` (WAV export) is built on top and unchanged for users.
- An LRU cache of the last 3 renders keyed on project + options.
- Renders are now deterministic: the reverb impulse is generated from a fixed seed and noise sources are seeded during offline renders, so stems add up exactly to the mix and analyses are repeatable. Verified: the demo's WAV export differs from the pre-refactor one by at most 1 LSB (−90.3 dBFS, the same as between two exports of the old code).

### F2 · Project schema v2 and migrations
- Projects are now schema v2: the same content plus optional fields for the coming features (sections, lyrics, annotations, reference track, linter settings, takes) and `meta` (`projectId`, `createdAt`, `updatedAt`).
- `src/migrations.ts` (pure): `migrate()` accepts v1 and v2 objects or JSON, fills missing defaults, assigns a stable `projectId` and rejects non-projects with a clear message. It is used by autosave, `import_project_json`, `.openband.json` and `.openband` files.
- Autosave moved to `openband.project.v2`; the v0.1 key is still read, so existing songs open and are re-saved as v2.

### F1 · Transactions and undo by intent
- Labelled undo history: each step records its label, source (UI/AI) and how many commands it groups.
- Store transactions (`beginTransaction` / `endTransaction`, nestable): commits inside one become a single undo step; empty transactions leave no trace.
- AI commands are grouped automatically and closed after 4 s of silence, or explicitly with the new MCP tools `begin_change(label)` / `end_change()`; a user edit closes an open AI step instead of merging into it.
- New MCP tool `get_history`; `undo` / `redo` take `steps`.
- Drags and knob turns are one step each. Undo/redo tooltips show the label; the AI panel groups activity by step with an “Undo this” button.
